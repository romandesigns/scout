# Scout V6.5.0 — Hybrid Production Integration Baseline

V6.5.0 is the first implementation release after the v6.4.13 architecture freeze.
It does not retune the validated detectors. It wires the selected architecture into
Scout's live runtime:

- Rust is the primary perception engine.
- Python remains the specialist/context/lifecycle engine and unique candidate source.
- Candidate provenance is persisted and correlated into hybrid episodes.
- Rust awakening candidates are enriched with Python market context before any alert.
- Recent Python alerts suppress redundant Rust awakening notifications.
- Notification consolidation merges dual-engine evidence and preserves the higher
  lifecycle priority.
- Shadow findings are explicitly non-notifying.
- Live hybrid precision and provider-accepted notification latency are exposed by
  `/api/status`.
- Feed connection/recovery telemetry is exposed in `/healthz` and `/api/status`.
- Same-session lifecycle state is restored from the persisted latest finding after a
  backend restart, reducing duplicate/rearmed alerts.
- The PWA displays `HYBRID LIVE` / `RUST DEGRADED` from live bridge state.

## Rust live bridge

The existing `scout-market-replay` crate now exposes a stateful `Engine::process_event`
method used by both replay and live streaming. The binary keeps its historical replay
CLI and adds:

```text
scout-market-replay --stream
```

`--stream` consumes `scout.market-event.v1` JSONL on stdin and emits fresh Rust
candidate transitions as JSONL on stdout. This preserves a single Rust state machine
for calibration and production.

The Python `RustPerceptionBridge` owns a bounded asynchronous queue so Alpaca websocket
processing is not blocked by Rust stdin I/O. If Rust exits, the supervisor restarts it
with backoff. Python Scout stays available and health reports the degraded state.

## Dormant-to-awakening notification policy

A Rust candidate remains the detector event. Python does not change the Rust recipe.
Before the event becomes an `AWAKENING` notification, Scout verifies current live
context is sufficiently actionable:

- Python market-quality state is `CLEAN`;
- Rust recipe score is at least 7;
- relative activity is awake;
- short-horizon price behavior is not inert.

Candidates that do not meet notification-layer quality remain persisted as silent
`PRE_IGNITION` findings. A Rust event arriving just after a Python lifecycle alert is
also persisted but shadowed to avoid redundant user notification.

## Lifecycle continuation

Existing Scout continuation/reclaim logic remains authoritative. `REARM` and
`FIRST_PULLBACK` notifications now carry explicit notification reasons indicating that
a controlled pullback held and momentum reaccelerated. This supports ILPT/DFNS-style
first-retest and multi-leg scenarios without adding a separate rigid chart-pattern
engine.

## Exact merged-stream measurement

Every market finding now carries:

- `engine_source`
- `hybrid_sources`
- `hybrid_score`
- `hybrid_key`
- `notification_reason`

`hybrid_key` groups candidate activity into 15-minute lifecycle episodes by ticker and
trading session. Once 15-minute outcomes are available, `/api/status` reports live
merged-stream precision at the configured threshold (`HYBRID_PRECISION_THRESHOLD_PCT`,
default +5%).

Notification delivery events were already persisted. V6.5.0 exposes recent median,
p95, and maximum provider-accepted latency from detection time by delivery channel.

## Production-readiness work still required after deployment

V6.5.0 provides the implementation hooks needed to measure these gates live, but the
following must be proven on the deployed Scout environment before a production-ready
release is declared:

1. Rust process stays healthy under the complete subscribed universe.
2. Rust bridge `dropped` remains zero under sustained load.
3. Live merged precision is acceptable after enough completed outcomes accumulate.
4. ntfy/Web Push delivery latency remains within the operational target.
5. Dormant → awakening notifications are observed before objective expansion in live
   or held-out replay scenarios.
6. Pullback/reacceleration lifecycle alerts behave correctly without duplication.
7. SIP/BOATS disconnect and reconnect telemetry behaves correctly.
8. Restart recovery does not recreate stale lifecycle alerts.
9. VPS, PWA, and Windows desktop remain healthy.
10. Coordinated release smoke test passes.
