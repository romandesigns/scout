# StockHunter Scout 6.3.0 — Pre-Ignition Intelligence Shadow

## Decision

Scout's primary mission is to warn when the ingredients for a bullish expansion are converging, before most of the move is consumed. A marker must always remain at the exact timestamp and price generated by the engine. The application must never move a late marker backward to an ideal historical location.

Version 6.3 introduces the data contract needed to improve timing without look-ahead bias. It does not claim that a pre-ignition recipe predicts an explosion, and it does not promote the new event to notifications.

## Lifecycle contract

| Phase | Meaning | Delivery in 6.3 |
| --- | --- | --- |
| `DEVELOPING` | Some ingredients exist, but the recipe is incomplete. | Silent |
| `ARMED` / `PRE_IGNITION` | The timestamp-safe recipe converged near a trigger while price remained near the base. | Shadow and silent |
| `IGNITING` | The first measurable release is underway. | Existing policy |
| `CONFIRMED` | Expansion and participation are established. | Existing policy |
| `REARM` | A later, independently evaluated compression releases. | Existing policy |
| `LATE` | Too much base extension existed at detection to describe the event as early. | Audit label; not a lifecycle rewrite |

## Timestamp-safe recipe

The shadow recipe is calculated only from information available at evaluation time:

1. compressed or orderly base;
2. price remains near the base;
3. price is pressing a nearby trigger;
4. EMA structure is improving;
5. relative volume is waking up;
6. participation is broadening;
7. price or volume is accelerating;
8. the short path avoids bearish structural failure.

The recipe score is an evidence score, not a probability. Present and missing ingredients are persisted verbatim so replay can explain why a candidate armed or failed to arm.

## Persisted audit fields

- lifecycle phase and shadow status;
- recipe evidence score;
- present and missing ingredients;
- trigger distance at detection;
- base extension at detection;
- timeliness label (`PRE_IGNITION`, `AT_IGNITION`, or `LATE`);
- precursor finding identifier on a subsequent release;
- exact detection time, price, formation bounds, trigger, invalidation, and engine version.

## UI behavior

- Shadow precursors use an orange `SHADOW · PRE_IGNITION` marker at the actual engine timestamp and price.
- Tooltips show timestamp, price, timeliness, and recipe score.
- Inspector shows lifecycle, shadow status, trigger distance, base extension, present ingredients, and missing ingredients.
- Confirmed detections keep their own independent markers. The chart never replaces one lifecycle event with another.

## Notification safety

`PRE_IGNITION` is explicitly silent in backend, web, Windows, Android, and email preferences. It has zero dispatch priority and does not enter the opportunity attention inbox. No new environment variable can enable it accidentally.

## Promotion gate

Promotion from shadow to an optional user alert requires representative replay and shadow-live evidence for:

- lead time before objectively defined expansion onset;
- move consumed at detection;
- false-arm rate;
- missed major expansions;
- behavior by session, liquidity, signal family, and market regime;
- detection-to-delivery latency;
- proof that every feature existed at its recorded timestamp.

Thresholds remain calibration hypotheses until those results are reviewed. Production 6.2 notification behavior remains the control.

## Release workflow

The permanent repository retains its ignored `.env`. From PowerShell 7, `prepare-release.ps1` validates version consistency, builds the frontend, runs the production Python 3.12 test environment, checks for staged secrets and whitespace, then commits and pushes an integration branch. Deployment remains an explicit `release-all.ps1` action after pull-request approval.
